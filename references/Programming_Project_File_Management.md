# 编程项目文件与 Git 管理

本文是[《项目初始化文档》](Project_Initialization.md)的编程专题，适用于脚本、应用、网站、工具和代码实验。核心代码及复现运行所需的项目文件由 Git 管理。项目开始时，同时确定**代码如何保存版本**和**代码是否可以推送**。本地提交、分支和标签可用于两类项目。

## 一、先确定项目发布模式

| 模式 | 远端怎么管理 | 工作怎么结束 |
| --- | --- | --- |
| **公开发布** | 登记获准的公开仓库、允许推送的分支，以及协作或发布流程。使用实际的推送地址核对目的地。 | 本地验证通过后，按项目约定推送分支、发起合并请求或发布版本。 |
| **本地专用，禁止推送** | 项目留在本地 Git 仓库。保持远端列表为空，禁用编辑器或客户端的自动发布与推送。 | 本地测试、提交、打标签和归档即可。该项目的分支和标签都留在本地。 |
| **发布模式待确认** | 先按本地流程工作。获得明确的公开范围和远端地址后，再启用公开流程。 | 汇报本地结果和提交号。 |

在项目入口按仓库登记工程路径与发布模式，供人和 AI 读取。公开发布项目还要说明**谁可以推送、可以推到哪里、是否通过合并请求**。AI 按当前任务的授权和项目约定执行。任务只涉及实现或检查时，汇报实际完成的本地工作即可。

如果同一项目同时维护公开代码和个人或 AI 专用代码，分别放在 `work/` 下的独立仓库，例如 `work/android/` 和 `work/local-tools/`。公开仓库只纳入获准发布的代码及可公开配置。专用代码放入独立的本地仓库，私有提示词、内部笔记和原始数据留在公开仓库根目录之外，按需通过本地配置接入。已经包含私有历史的本地仓库要转公开时，从获准公开的文件建立干净的公开仓库，再按公开流程核对和推送。

## 二、目录和文件怎么分

新编程项目初始化时，在 **`work/` 下直接建立一个按平台或工程用途命名的二级目录**，即使目前只有一个工程。Android 项目从 `work/android/` 开始，源码、测试、构建配置和 Git 仓库都放在这个工程目录内，并沿用技术栈的内部结构。后续确定开发 Web 或 iOS 时，再添加并列的 `work/web/` 或 `work/ios/`。

### 项目外层

| 路径 | 用途 |
| --- | --- |
| `README.md` | 整个产品或项目的入口，记录目标、当前任务、各工程入口和推送模式。 |
| `inputs/` | 原始需求、设计稿、收到的接口文档和原始数据。有输入时建立。 |
| `management/` | `project.json`、任务详情、共用产品决策和验收记录。项目看板仍以产品或项目为单位。 |
| `work/` | 工程和开发文件。初始化时建立首个工程目录。确有共用开发文档时可放 `work/docs/`，由项目入口链接。 |
| `deliverables/` | 收到正式交付指令后，按需保存或登记产物。多平台可按平台和版本分目录。 |
| `archive/` | 仍需保留的旧方案与历史资料，按需建立。 |

### 工程目录和 Git 根目录

| 情况 | 工程目录及 Git 根目录 |
| --- | --- |
| 单独的 Android、iOS 或 Web 工程 | 按实际平台使用 `work/android/`、`work/ios/` 或 `work/web/`。 |
| 单脚本、命令行工具或后端 | 按工程用途命名，例如 `work/tool/`、`work/cli/` 或 `work/backend/`。单脚本可直接放在该工程目录。 |
| 多个独立工程 | 在 `work/` 下并列放置各工程。各仓库分别登记运行方式、远端和推送权限。 |
| 一套代码的跨平台工程 | 使用一个工程目录，例如 `work/app/`。Git 根目录在 `work/app/`，框架生成的 `android/`、`ios/` 等目录随该工程维护。 |
| 已有工程 | 保留现有 Git 根目录和工程结构，由项目入口链接过去。以后确实需要迁移时，再更新工程路径和引用，并验证 Git 历史、构建与测试。 |

### 工程内部

以下路径以工程根目录为起点。例如 Android 的运行说明是 `work/android/README.md`，外层 `README.md` 链接到它。

| 位置或文件 | 内容 | Git 管理方式 |
| --- | --- | --- |
| `README.md` | 项目用途、发布模式、安装、运行和验证命令。 | 纳入版本控制。公开仓库使用可公开的内容。 |
| `src/` 或框架默认位置 | 应用代码、脚本、模板和必要资源。 | 纳入版本控制。单脚本可放仓库根目录。 |
| `tests/` 或现有测试位置 | 测试代码和运行所需的少量样例。 | 纳入版本控制。公开仓库使用可公开的样例或模拟数据。 |
| 依赖声明、适用的锁文件、构建脚本 | 依赖、工具链和可复现的构建或运行方式。 | 按项目技术栈纳入版本控制。 |
| `docs/` 或现有文档位置 | 架构、接口、使用说明和需要随代码维护的决策。 | 按项目需要跟踪，公开仓库仅保留可公开版本。 |
| `AGENTS.md` | 有持续 AI 协作需求时，记录运行与测试命令、编辑边界、项目惯例和推送规则。 | 按需建立。公开仓库中仅写可公开的协作规则。 |
| `.gitignore`、`.env.example` | 忽略规则和可复制的配置样例。 | 纳入适用的文件。样例只写字段和占位值。 |
| 本地配置、凭据、缓存、依赖安装目录、可重建产物 | 例如 `.env`、本机路径、日志和构建缓存。 | 用本地文件、环境变量或工具专用位置保存，并按需添加忽略规则。 |

`.gitignore` 只作用于未跟踪文件。已经跟踪的文件仍需检查暂存区和历史，尤其是在首次公开前。 [Git 官方文档 · gitignore](https://git-scm.com/docs/gitignore)

## 三、初始化 Git

### 两类项目的共同起点

在**尚未初始化的工程目录**中运行以下命令，例如 `work/android/`。示例默认分支为 `main`。已有仓库先用 `git rev-parse --show-toplevel` 定位根目录，再沿用原有分支和历史。已有公开协作仓库时，从获准的地址取得代码并核对已有远端。

```bash
git init -b main
git status --short
git remote -v
```

先准备入口、忽略规则、代码和适用的依赖文件。检查将要提交的内容，再建立首个本地提交。目录名和文件名按实际项目选择。 [Git 官方文档 · git-init](https://git-scm.com/docs/git-init)

### 公开发布项目

首次连接远端前，确认公开范围、仓库地址和分支要求。首次推送时检查拟公开分支及标签所指向的历史，包含曾经提交又删除的文件。后续推送检查即将发布的提交和实际内容。

以下示例适用于**获准直接向全新空仓库推送、目标分支为 `main`、本地已有提交**的情况。先替换示例地址，再逐步执行。已有远端时，核对现有设置。协作仓库按约定推工作分支，再走合并流程。

```bash
git remote add origin https://example.com/owner/repository.git
git remote get-url --push --all origin
```

确认列出的每个推送地址都在本次授权范围内，并核对拟发布历史后，执行明确的分支推送。

```bash
git push -u origin main
```

已有远端分支时，可在更新远端引用后，用 `git log -p origin/main..HEAD` 辅助查看当前分支相对 `origin/main` 的待发布提交和补丁。目标分支变化时换成对应引用。 [Git 官方文档 · git-remote](https://git-scm.com/docs/git-remote) · [git-push](https://git-scm.com/docs/git-push) · [git-log](https://git-scm.com/docs/git-log)

### 本地专用项目

新仓库保留空的远端列表，用 `git remote -v` 检查。接手已有本地仓库时，先核对已有远端，确认用途后清理旧配置。创建、修改、测试、提交和打标签都在本地完成。看到工具的「发布仓库」「推送」选项时，继续使用本地提交。交接时登记本地路径、分支和提交号。

需要减少误推时，可以加一个本地 `pre-push` 钩子。默认钩子文件为 `.git/hooks/pre-push`。配置了 `core.hooksPath` 的仓库使用实际钩子目录。已有同名钩子时，把拒绝逻辑合并进去。

```sh
#!/bin/sh
printf '%s\n' 'This repository is local-only. Git push is disabled.' >&2
exit 1
```

在默认钩子位置保存后，用 `chmod +x .git/hooks/pre-push` 使脚本可执行。该钩子可拦截正常的 Git 推送，也适用于直接指定目标地址的推送。命令的 `--no-verify` 可跳过钩子。需要由环境强制禁推时，把限制落实到该环境的远端访问或网络权限。 [Git 官方文档 · githooks](https://git-scm.com/docs/githooks) · [git-push](https://git-scm.com/docs/git-push)

## 四、日常提交和版本怎么管理

| 操作 | 怎么处理 |
| --- | --- |
| **开始任务** | 确认当前分支、现有改动和任务范围。多人协作或需要隔离试验时，使用工作分支。 |
| **编辑与验证** | 在同一份源文件上维护代码，执行项目约定的运行、测试或构建命令。依赖或运行方式有变化时同步更新配置和说明。 |
| **本地提交** | 只暂存本次任务相关文件，用 `git diff --cached` 看实际将提交的改动。每个提交尽量对应一个可说明的变更。 |
| **推送或留在本地** | 公开项目按授权核对待发布的历史与目的地，再推送指定分支。本地专用项目到本地提交为止。 |
| **标记可用版本** | 需要标记交付或可回退节点时，登记 Git 提交号或标签。构建产物和验收记录注明对应版本。 |

区分三条记录。**任务表**说明为什么改、当前做到哪。**Git 历史**记录代码、配置和相关文档怎么变。**交付记录**关联可用版本、验收结果和产物位置。交付的是一次本地运行结果时，同样可以记下对应提交和复跑命令。

## 五、各阶段的文件怎么流转

| 阶段 | 工作动作 | 要留下的记录 |
| --- | --- | --- |
| **立项与初始化** | 确定目标、首项功能和发布模式。找到或建立 Git 根目录，写明运行和验证入口。 | 项目入口、发布模式、首项任务和初始提交。 |
| **开发与验证** | 更新代码、配置和必要说明，运行约定的验证。把生成物放到约定位置。 | 有意义的本地提交、验证结果和待处理问题。 |
| **审阅与验收** | 检查变更范围、实际行为和拟交付版本。发现问题时，修改源文件并复验。 | 审阅意见、对应提交和验收结论。 |
| **交付与维护** | 公开项目按授权推送或发布。本地专用项目提供本地路径、运行步骤、提交号或标签。 | 交付版本、产物或链接、运行方式和后续维护位置。 |
| **结项与归档** | 保留可编辑源码、Git 历史、必要配置说明、交付产物和复现所需输入。 | 可追溯到交付版本的归档记录。本地专用项目沿用本地归档方式。 |

本地项目需要备份时，确认备份覆盖 Git 历史及必要的未跟踪输入。恢复后检查仓库能读取、目标提交可定位、项目可运行。项目暂停时，记录停在哪个分支、最后可用的提交、当前未完成的改动及恢复条件。

## 六、给人和 AI 的交接模板

```markdown
## 任务 [简述变更]

- 项目模式 [公开发布 / 本地专用，禁止推送 / 待确认]
- Git 根目录与工作分支 [路径和分支]
- 当前基线 [提交号、标签或已有工作状态]
- 输入与编辑范围 [任务、文件、接口和依赖]
- 验收方式 [测试或构建命令、预期行为]
- 交付动作 [本地修改 / 本地提交 / 推送指定分支 / 其他已授权动作]
- 结果记录 [变更、实际运行的检查、提交号和待办]
```

## 七、初始化与交付检查

- [ ] 新工程在 `work/` 下使用按平台或用途命名的目录，项目入口登记各仓库的发布模式、Git 根目录、运行和验证方式。
- [ ] 核心代码、必要配置和依赖文件已纳入适用的 Git 版本控制。
- [ ] 本地专用项目的远端列表为空，协作规则写明禁止推送。
- [ ] 公开项目在推送前已核对目的地、分支、待发布内容和相关历史。
- [ ] 能从交付记录找到对应的提交或标签，以及复现所需的文件和步骤。
