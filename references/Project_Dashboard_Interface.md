# 综合项目看板接口使用文档

本文记录综合项目看板的任务读写约定，供后续开发使用。项目初始化与目录规则见[《项目初始化文档》](Project_Initialization.md)。

第一版的使用方式是**在本地看板新增任务，在项目的 Agent 里指定任务执行，执行结果回写看板**。例如，在看板为某个 App 新增「增加 Android 月报功能」，保存后得到任务号 `T014`，再到该项目的 Agent 会话说「执行 T014，完成后写回看板」。看板保存任务时进入待办，Agent 开始执行由用户在会话中触发。

## 一、项目侧保留哪些文件

| 路径 | 职责 | 维护方式 |
| --- | --- | --- |
| `README.md` | 项目入口，链接到工程、看板接口和相关项目规则。 | 在项目内维护。 |
| `management/project.json` | 项目概况、任务列表、状态、下一项任务。看板通过 `project_id` 识别项目。 | 初始化时建立。接入可写看板后，任务字段经同一个服务写入。 |
| `management/tasks/T014.md` | 任务目标、工作范围、验收条件、执行结果和验证依据。 | 第一次需要独立任务详情时建立 `tasks/`。看板新增任务时生成详情，Agent 通过服务追加结果。 |
| `work/android/` | 示例任务的目标工程，包含源码、测试和 Git 仓库。 | Agent 在用户授权的项目工作区内按任务要求执行。 |

看板在本机登记 `project_id` 与实际目录的对应关系。项目移动时重新绑定目录，沿用原 ID。两个目录出现相同 ID 时，在确认使用哪一个之前只展示冲突。任务文件中的路径相对项目根目录。服务根据已登记的目录解析路径，拒绝指向其他项目或越出项目根目录的路径。

### 兼容现有项目

- 沿用 `schema_version: 1` 及主文档的现有字段。看板应当能读取旧记录，保留自己不认识的字段。
- `revision` 是可选的整数版本。缺少时按 `0` 处理，首次由服务成功写入后递增。用于识别客户端读到的记录是否过期。
- 看板新增的任务在 `tasks` 中至少登记 `id`、`title`、`status`、`detail_path`。可选字段 `target_path` 用于快速定位目标目录，`created_at` 记录创建时间，`run_id` 用于识别正在执行的任务批次。旧任务可以继续使用 `detail_url` 或只有索引字段。
- 如果任务已由外部工具统一维护，仍由该工具作为任务来源。第一版的本地看板把这类项目显示为只读，等有对应的写入适配再启用新增或状态更新。

## 二、在看板上新增一条任务

以「给 Android 版增加月报」为例。看板表单可按下列信息收集任务。

| 表单字段 | 示例 |
| --- | --- |
| 标题 | 增加 Android 月报功能 |
| 目标工程 | `work/android/` |
| 目标与范围 | 支持选择月份，展示该月支出总额和分类汇总。 |
| 验收条件 | 汇总与同月账目一致。切换月份后刷新结果。无账目时显示空状态。 |
| 参考与约束 | 复用现有账目数据与分类规则。明确实际采用的月份边界。推送按工程已有规则执行。 |

点击保存后，由服务分配项目内唯一的任务 ID，保存任务详情，再登记任务索引。状态初始为 `todo`。ID 分配在项目内串行处理，取消的任务保留记录和原 ID。保存成功后，看板显示任务号、详情和可复制的 Agent 指令。普通新增任务沿用已有的 `next_task_id`，只有明确选择「设为下一项」时才更新该字段。

以下是已保存任务的 `management/project.json` 示例。真实项目应保留自己的其他任务。

```json
{
  "schema_version": 1,
  "revision": 8,
  "project_id": "expense-app",
  "name": "示例账本",
  "type": "programming",
  "summary": "开发用于记录和汇总支出的应用。",
  "status": "active",
  "stage": "执行与调整",
  "updated_at": "2026-11-13T11:40:00+08:00",
  "entry_path": "README.md",
  "next_task_id": "T014",
  "tasks": [
    {
      "id": "T014",
      "title": "增加 Android 月报功能",
      "status": "todo",
      "target_path": "work/android/",
      "detail_path": "management/tasks/T014.md",
      "created_at": "2026-11-13T11:40:00+08:00"
    }
  ]
}
```

对应的 Markdown 可由看板按这个结构生成。索引维护状态，详情维护任务内容和执行记录。

```markdown
# T014 增加 Android 月报功能

## 目标与范围

- 在 Android 版增加按月查看的支出总额和分类汇总。
- 工作位置为项目根目录下的 work/android/。
- 复用现有账目数据与分类规则。

## 验收

- 所选月份的合计与同月账目一致。
- 切换月份后总额和分类汇总同步更新。
- 无账目时显示空状态。

## 执行记录

执行后记录变更、验证命令及结果、遗留事项和 Git 提交号（如有）。
```

## 三、Agent 怎样执行并回写

### 从项目会话登记需求

用户提出具体的项目改动、交付或验证需求时，先核对项目和已有任务，再在同一轮登记标题、范围、验收条件和工作位置。用户补充或纠正同一需求时，更新原任务详情并沿用编号；独立交付事项另建任务。普通问答、只读状态查询和继续已有任务沿用当前记录。

- 看板服务或外部任务系统已接入时，通过正式来源创建或更新任务。任务由本地索引维护时，在技能目录执行 `python3 scripts/project_init.py add-task <项目目录> --title "<标题>" --scope "<范围>" --acceptance "<验收条件>" --target-path "<项目内工作目录>"`。工作目录默认为 `work/`，可指定其他已有目录。命令同时写入任务详情和索引，初始状态为 `todo`，保留已有的下一项安排。用相同参数重试可取得已登记的任务。
- 用户已要求执行时，登记后直接开始，状态更新为 `in_progress`。用户要求仅登记时保留为 `todo`。需要补充关键条件才能执行时，先登记已知内容，再在任务详情注明缺项及恢复条件，按阻塞或搁置流程处理。
- 验收通过后，写入实际结果和成果链接，再标记 `done`。按下文流程复读索引和详情，确认状态和记录一致。回复时给出任务编号与最终状态。若只能核对本地索引，明确看板界面的刷新尚未核对。

### 执行和回写

用户在该项目的 Agent 会话里输入：

> 执行 T014。按任务的验收条件验证，完成后把结果写回看板。

1. **定位任务。** 从当前项目的入口和 `management/project.json` 确认 `project_id`，按任务 ID 获取详情，读取目标工程的运行、测试和推送规则。跨项目使用任务 ID 时同时传项目 ID。
2. **开始执行。** 服务确认任务可开始后，将状态从 `todo` 改为 `in_progress`，返回本轮的 `run_id`。同一任务已经在执行时，告知当前状态，由用户决定是否继续原会话。
3. **实现与验证。** 在任务范围内修改目标工程，按验收条件运行检查。对影响实现结果的缺项，例如月报的统计时间边界无法从现有规则确定时，写明具体缺项并标记阻塞。
4. **回写结果。** 将变更摘要、验证命令和实际结果、未解决项、输出路径及 Git 提交号（如有）写入任务详情。验收通过后标记 `done` 并写入 `completed_at`。阻塞时登记 `blocked_reason`。
5. **刷新看板。** 看板重读项目索引与任务详情，按状态展示结果。若完成、阻塞或取消的是当前 `next_task_id`，将其清空，之后由用户或已有项目计划选定下一项。

第一版采用 `todo → in_progress → done / blocked`。阻塞项补齐条件后可回到 `todo`。取消使用 `cancelled`，保留已有执行记录。重新安排被中断的任务时，可显式退回 `todo` 并撤销旧 `run_id`。完成、阻塞及进行中的写回须匹配当前 `run_id`，避免旧会话覆盖新结果。取消或退回待办只改变任务记录，已运行的 Agent 会话需在其会话中停止或调整。

Git 提交、推送、发布和正式交付按工程与当前任务的授权执行。禁止推送的仓库始终按本地流程处理。看板状态更新和任务执行可以用于编程、写作和视频项目，差异由任务的目标路径及验收条件表达。

### 搁置与看板登记

用户明确搁置具体项目事项时，在本轮写入任务详情和任务索引。记录搁置原因、恢复条件及必要的接手信息。用户未给出恢复时间时，写「用户决定继续时恢复」。README 或结项记录需要提及时，链接同一任务详情。

- **已有任务**沿用原 ID。**尚未编号的事项**先查找同一事项，确需新增时登记为 `blocked`。索引保留 `detail_path` 或正式来源的 `detail_url`，并填写 `blocked_reason`。搁置的是下一项时清空 `next_task_id`，保留其他下一项安排。将已运行的任务搁置时，旧执行编号失效，后续执行从恢复任务开始。
- **本地索引**使用 `python3 scripts/project_init.py defer <项目目录> --task-id <ID> --reason <原因> --resume-when <恢复条件>`。尚无 ID 时用 `--title <标题>`，相同标题会沿用已有任务。可用 `--record <Markdown文件>` 补充已讨论的方案或链接。
- **任务服务或外部系统**通过正式来源登记。只有读到索引或服务返回中的任务 ID、`blocked` 状态和可读详情，才报告已登记。可读本地索引时用 `inspect` 与 `task` 复核；能访问看板界面时再刷新核对。写入失败时说明哪部分尚未登记。

## 四、将来看板和 Agent 对接哪些操作

本地看板、轻量命令和后续 MCP 都可接入同一任务服务。先实现表中的操作即可，命令名是供未来实现参考的约定。

| 操作 | 建议命令或调用 | 输入与返回 |
| --- | --- | --- |
| 读取项目 | `project show <project_id>` | 返回项目概况、任务索引和 `revision`。 |
| 新增任务 | `task create <project_id>` | 传标题、目标路径、范围、验收、可选参考与是否设为下一项。返回任务 ID、详情路径、状态和新版本。 |
| 读取任务 | `task show <project_id> <task_id>` | 返回任务索引、正文、可用的执行信息和当前版本。 |
| 开始任务 | `task start <project_id> <task_id>` | 比对版本和状态。成功后返回 `run_id` 及新版本。 |
| 完成任务 | `task finish <project_id> <task_id>` | 传 `run_id`、结果和验证信息。追加记录，更新状态和版本。 |
| 标记阻塞 | `task block <project_id> <task_id>` | 传 `run_id` 和阻塞原因。追加记录，更新状态和版本。 |
| 调整待办 | 看板中的「恢复待办」「取消」「设为下一项」 | 传目标任务和当前版本，按状态规则处理，返回新版本。 |

写操作携带客户端上次读取的 `expected_revision`。服务在同一项目的写锁内重读当前版本再判断。遇到版本冲突，返回当前版本，客户端重新读取并核对自己的修改。创建任务使用同一 `request_id` 重试时，应返回原任务，防止双击或断线重试生成两条待办。

### 保存和故障恢复

- 看板和 Agent 统一通过服务改任务索引。每次写入只修改本操作负责的字段，保留其他任务和项目字段。
- 文件使用 UTF-8。写入 JSON 和 Markdown 时先写临时文件，再替换目标。一次操作涉及两份文件时，先保存详情或结果，再提交索引与 `revision`。界面只在服务确认完整保存后提示成功。
- 服务实现时应保留本次写入的操作记录，记录请求标识、任务 ID 和预期状态。遇到中断，恢复时用它确认已落盘的步骤，补齐或撤回未提交的更新。重试同一操作应避免重复追加执行记录。冲突无法自动恢复时显示具体项目和任务，供人工核对。
- 第一版看板应在写入成功后重读数据。Agent 或另一窗口的变化可通过定时刷新或手动刷新显示，后续再考虑即时推送。

## 五、实现时用这个流程验收

1. 登记一个已有 `management/project.json` 的项目，确认看板能加载旧任务。
2. 在看板创建「增加 Android 月报功能」，确认 Markdown 和索引都落在该项目的 `management/`，刷新页面后仍可找到。
3. 在项目的 Agent 会话指定任务 ID，确认能读取详情和工程路径。开始时看板显示进行中，重复启动时提示已有执行。
4. 写回验证结果，确认看板显示完成并可查看实际记录。再用另一条任务测试阻塞、补齐条件和恢复待办。
5. 用两个窗口测试旧版本提交，用同一请求测试重复创建，并模拟详情保存后索引尚未提交的中断，确认恢复后任务只出现一次。

当前交付的是接口约定和示例。看板界面、本地服务、命令和 MCP 由后续开发实现。
