# 项目初始化文档

每个项目用 `README.md` 作为入口，写清目标、当前范围、验收条件、下一步和关键文件位置。人和 AI 从同一入口接手。项目概况和任务状态在 `management/project.json` 维护，供综合项目看板读取。

## 一、收到「初始化」后怎么做

在新建的项目中收到「初始化」，先根据用户已经提供的信息，集中询问仍缺少、且会影响开工的问题。优先问下面四项，已经明确的内容直接使用。

| 要了解的信息 | 可以怎么问 |
| --- | --- |
| 项目类型 | 这是 AI 视频、编程、写作，还是其他类型？如果是写作，偏编剧、小说，还是其他形式？ |
| 目标和使用场景 | 想解决什么问题或做出什么成果？给谁用，用在什么场景？ |
| 本阶段范围与验收 | 第一阶段做到什么程度？有哪些边界？怎样判断第一阶段做完了？ |
| 已有输入与限制 | 有哪些资料或已有成果？有无期限、协作分工、工具、格式、公开范围等限制？ |

根据项目类型只追问必要信息。例如，视频可问时长和画幅，编程可问仓库推送范围，写作可问载体、篇幅和当前稿件阶段。目标尚不明确时，把调研、试做或梳理需求设为第一项任务。暂时没有答案的次要问题写入「待决定」，并标明影响哪一步。

收到回答后，按以下顺序建立或补齐项目文件。

1. 在 `README.md` 记录目标、范围、验收条件、约束和正式链接。
2. 建立 `work/` 与 `management/project.json`，按需建立其他目录。已有项目保留其工作位置，并补齐入口和看板接口。
3. 登记第一项任务，写清输入、动作、产出位置和完成条件。已有任务或资料时，沿用其编号和位置。
4. 从入口走一遍第一项任务，确认接手者能找到输入、知道从哪里开始，以及如何检查结果。

## 二、目录与文件职责

| 位置 | 放什么 | 何时建立 |
| --- | --- | --- |
| `README.md` | 项目入口。放目标、范围、验收、约束、下一步和正式链接。 | 初始化时。 |
| `AGENTS.md` | AI 协作时需要长期遵循的项目规则。 | 按需建立，见下文。 |
| `inputs/` | 原始需求、收到的素材、调研资料和外部参考。 | 有独立输入文件时。 |
| `work/` | 可编辑主稿、中间产物、审阅快照，以及复现成果所需的工作文件。 | 初始化时建立，子目录按需增加。 |
| `management/project.json` | 项目概况、进度与任务索引，供看板读取和后续接入任务服务。 | 初始化时。 |
| `management/tasks/` | 通过 `detail_path` 关联的独立任务详情和执行记录。 | 首次需要独立任务详情时。 |
| `management/` 内其他记录 | 任务详情、决策、里程碑、验收和交接记录。 | 入口或单条任务已容纳不下时。 |
| `deliverables/` | 正式交付的文件、版本清单或外部交付链接记录。 | 用户明确提出交付，且需要在项目内登记或存放时。 |
| `archive/` | 退出日常使用、仍需保留的历史文件。 | 有明确归档对象时。 |

工作文件较多时，优先按成果或稳定模块建立子目录，例如 `work/guide/` 和 `work/checklist/`。草稿、审阅、通过等状态记在任务或版本记录里。已有仓库、专业软件工程或在线协作空间时，从入口链接到对应位置。

### 是否需要 `AGENTS.md`

按需建立，采用文件名 **`AGENTS.md`**。持续用 AI 协作、经常换会话，或项目有需要反复执行的目录、验证、发布规则时，放一份简短的 `AGENTS.md`。单次任务可以在 `README.md` 或任务记录中说明要求。Codex 的项目指令查找支持 `AGENTS.md`，在独立代码仓库中协作时，仓库专属规则可放在该仓库根目录。 [Codex 官方文档](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

- `README.md` 回答项目做什么、资料在哪里、现在从哪一步开始。
- `AGENTS.md` 记录稳定的操作规则，例如先读哪个入口、用哪个命令验证、哪些目录可编辑、是否允许推送，以及正式交付的触发条件。
- 具体任务进度放在看板接口，任务详情放在对应记录。已有 `AGENTS.md` 时，在原文件补充适用规则。

### 文本格式

策划、剧本和小说工作稿、规范、日志、说明和审阅意见等，以 UTF-8 Markdown（`.md`）作为默认可编辑格式。结构化接口用 JSON，适合按行列维护的记录可用 CSV 或项目已有表格。原始输入保留原格式，专业工程保留工具的源文件。需要版式、批注兼容或正式交付时，按实际用途选择 Word、PDF、EPUB 等格式。

## 三、生命周期与各阶段文件管理

| 阶段 | 新建或更新什么 | 怎么收尾 |
| --- | --- | --- |
| **提出与立项** | 在入口记录问题和目标。原始需求与调查资料放 `inputs/`，试做放 `work/`。 | 记录启动、暂缓或取消的决定及依据。启动后标明采用的输入。 |
| **初始化与计划** | 写明范围、验收和首项任务。建立看板接口，记录项目状态和首项任务。 | 从入口能找到正式输入、主稿或预定保存位置及首项任务。 |
| **执行与调整** | 在 `work/` 编辑主稿，更新任务状态和阻塞。新输入归入 `inputs/`。范围、期限或验收变化时，记录决定。 | 内部审阅使用具体版本链接或工作快照。 |
| **内部验收** | 按验收条件检查，登记通过项、待修项和被检查的版本。 | 通过后将相应任务标为完成。工作成果保存在工作位置。 |
| **正式交付** | 用户明确提出交付后，按指定对象、用途、范围和格式准备成果。 | 登记交付版本、位置和日期。需要打包时再制作交付包。 |
| **试运行与移交** | 有试用或维护需求时，记录反馈、待修任务、接手人、维护方式及依赖位置。 | 接手人能定位当前成果、源文件和反馈入口。 |
| **结项与归档** | 更新项目状态，记录关键决定、遗留事项、工作成果及已有交付记录。 | 保留修订和追溯所需的文件。移动旧文件后核对引用。 |

**正式交付由用户明确提出。** 完成任务、内部验收、回复进度或结项时，继续按工作文件的规则保存成果。未收到交付指令时，不打包项目、不生成正式交付件、不发布或发送成果。收到交付指令后，先判断直接提供指定文件、版本链接或记录是否足够，再按实际需要打包。交付清单按范围登记文件、版本和位置。

项目暂停时，记录原因、当前进度、源文件位置和恢复条件。恢复时先核对条件，再确定下一步。取消时，记录终止决定和已承诺事项的处理结果。多阶段项目可分轮执行和验收，交付仍以明确指令为准。

### 结项、迁移与重启

1. **整理结项记录。** 核对验收结果和任务状态，明确遗留事项如何交接。在 `management/closeout.md` 追加本轮日期、成果和源文件入口、验证结果、关键决定、遗留事项及已有交付记录。将相关 Codex 聊天里的决策和接手信息写入记录，按可得信息注明聊天标题、日期或入口。原聊天留在 Codex。让项目入口链接到结项记录；使用相对于记录文件的项目内链接。重复结项时补充同一轮记录，保留各轮历史。
2. **登记结项与选择归档位置。** 本地索引用 `python3 scripts/project_init.py closeout <项目目录>` 将项目设为 `completed`，阶段设为「结项与归档」，清空下一项，保留任务历史。若由看板服务或外部系统维护，则通过正式来源更新。请用户在以下方式中选择，已有明确选择时直接采用。等待选择期间可完成结项记录，将归档位置记为待选。
   - **原地归档**：保留当前项目目录。检查入口、任务、成果链接和必要依赖，在结项记录登记归档日期、现有路径和核对结果。
   - **同级 `_Archive`**：将整个项目移到当前项目的同级归档目录，例如 `/工作区/项目` 移到 `/工作区/_Archive/项目`。
   - **自定义目录**：将整个项目移到用户指定的父目录下，保留原项目目录名。
3. **选定迁移方式后整体移动并验证。** 先列出源路径和完整目标路径，核对目标不存在且位于源目录外，确认目录权限及外部依赖，遇同名项目时请用户选新的位置。整体保留入口、管理索引、任务记录、工作文件和已有交付物。若跨卷，先完整复制并验证，再移除原目录。用新路径检查入口、任务、成果链接和必要依赖，保留 `project_id`。已有看板登记时更新路径绑定。把迁移日期、目标路径和核对结果记入结项记录。用户级已安装的技能留在个人技能目录。
4. **已结项项目重启。** 用户要求继续开发、修订规范或执行新任务时，开始前把项目恢复为 `active`，阶段记为「项目重启」。如果实质改动已经发生，发现时补记。本地索引用 `python3 scripts/project_init.py reopen <项目目录>`；看板或外部系统走原接口。保留原项目 ID、旧任务和结项记录，在结项记录追加重启日期、原因和本轮范围，并按需登记新任务。已迁移的项目先沿用当前位置，需要搬回工作区时由用户指定。只读查询、验证已归档文件和补充归档记录沿用已结项状态。

上述命令从技能目录运行，用于更新本地索引。结项记录、目的地选择和文件迁移由 Agent 按步骤处理。

## 四、综合项目看板接口

固定入口为项目根目录下的 **`management/project.json`**。这是供综合看板读取的文件约定。看板按项目目录读取该文件，使用稳定的项目 ID 合并展示。项目概况、任务状态和更新时间在此维护，长任务详情通过路径或链接指向原记录。看板新增的任务详情默认保存在 `management/tasks/<任务ID>.md`，通过 `detail_path` 关联。

本地可写看板接入后，看板和 Agent 通过同一个任务服务新增任务和回写状态。用户在项目会话中指定任务 ID 启动执行。文件字段、任务操作、写入冲突和恢复约定见[《综合项目看板接口使用文档》](Project_Dashboard_Interface.md)。

### 可复制的最小示例

```json
{
  "schema_version": 1,
  "project_id": "demo-guide",
  "name": "示例指南",
  "type": "writing",
  "summary": "编写一份可供新同事独立使用的操作指南。",
  "status": "active",
  "stage": "执行与调整",
  "updated_at": "2026-11-13T10:00:00+08:00",
  "entry_path": "README.md",
  "next_task_id": "T002",
  "tasks": [
    {
      "id": "T001",
      "title": "确认指南范围和章节",
      "status": "done",
      "completed_at": "2026-11-13T09:30:00+08:00"
    },
    {
      "id": "T002",
      "title": "编写第一章并验证操作步骤",
      "status": "in_progress"
    },
    {
      "id": "T003",
      "title": "核对术语并补齐示例",
      "status": "todo"
    }
  ]
}
```

| 字段 | 约定 |
| --- | --- |
| `schema_version` | 接口版本，当前为整数 `1`。发生不兼容的字段或含义变化时提升版本。 |
| `project_id` | 在综合看板中唯一且稳定。改名或移动目录时沿用原 ID。 |
| `name`、`type`、`summary` | 项目名称、类型和简述。类型用 `ai_video`、`programming`、`writing` 或 `other`。 |
| `status`、`stage` | 项目整体状态和当前阶段。状态用 `planned`、`active`、`paused`、`completed`、`cancelled`。阶段用第三节中的可读名称。已结项后恢复工作用 `active` 与「项目重启」。 |
| `updated_at`、`entry_path` | 接口最后更新时间和项目入口。时间带时区，文件路径相对项目根目录。 |
| `next_task_id` | 指向一个可推进的任务 ID。暂无下一步时填 `null`。 |
| `tasks` | 任务数组。每项含稳定的 `id`、`title`、`status`。按需补充 `detail_path`、`blocked_reason` 或 `completed_at`。暂无任务时填 `[]`。 |

任务状态使用 `todo`（待办）、`in_progress`（进行中）、`blocked`（阻塞）、`done`（已完成）和 `cancelled`（取消）。看板按状态列出待办、进行中、阻塞和已完成。进度由**已完成任务数 ÷ 未取消任务数**计算，分母为零时显示「暂无可统计任务」。需要判断阶段进展时，同时查看 `stage` 和阻塞项。任务 ID 在项目内唯一。任务详情用相对项目根目录的 `detail_path`，位于外部工具时可用 `detail_url`。

项目名称、概况、阶段、任务状态或下一步发生变化时，更新此文件及 `updated_at`。可写服务接入前，项目成员在项目内维护记录。接入后，任务写入走统一服务。任务有独立看板时，可由该工具生成接口文件，任务状态以该工具为唯一维护位置。上面的例子用于核对读法和字段，初始化实际项目时换成真实信息。

## 五、专题怎么选

所有专题保留顶层 `work/`。同一项目涉及多种工作时，可按实际工作启用多个专题，确有分区需求时再建工作流子目录。

| 专题 | 主要管理对象 | 从哪里开始 |
| --- | --- | --- |
| AI 视频制作 | 策划、分镜、角色和场景资产、镜头生成、后期工程。 | 按[AI 视频专题](AI_Video_Project_File_Management_v2.md)建立策划和镜头入口。 |
| 编程 | 核心代码、依赖、测试、构建、Git 历史及推送范围。 | 新项目按[编程专题](Programming_Project_File_Management.md)在 `work/` 下创建首个工程目录，例如 `work/android/`。已有仓库沿用现有位置。 |
| 写作 · 编剧 | 策划、大纲、人物、分场、剧本和修改意见。 | 单一写作项目在 `work/` 维护大纲、分场和剧本主稿。有分场修订或交接需求时，给场次稳定编号。 |
| 写作 · 小说 | 设定、人物、大纲、章节主稿和修改记录。 | 单一写作项目在 `work/` 维护大纲和设定。长篇可用 `work/chapters/` 并建立章节索引，短篇可用 `work/manuscript.md`。 |

编剧和小说的目录、主稿版本、审阅和交接规则见[写作专题](Writing_Project_File_Management.md)。

这份文档作为后续制作项目初始化 Skill 的流程规范。收到用户明确提出制作 Skill 的指令时，再将询问流程、目录与接口模板、专题选用和检查项写入 Skill。

## 六、命名、版本和交接

1. **每项信息指定一个正式维护位置。** 主稿在同一位置编辑，关键选择更新到决策记录，状态更新到看板接口或生成该接口的正式任务工具。入口链接到相关位置。
2. **文件名体现对象和用途。** 例如 `guide.md`、`requirements.md`。同一项目统一语言和分隔符。日期用于日期相关记录，版本号用于需要保留的快照。
3. **固定审阅和交付版本。** 日常编辑使用已有版本历史。审阅时登记可定位的版本，必要时在 `work/` 保存快照。正式交付后登记实际提供的版本。
4. **保持引用可用。** 项目内优先用相对路径，跨工具使用可访问的链接。移动或重命名后，检查入口、任务和主稿依赖。
5. **交接写清执行条件。** 任务记录应能找到输入、编辑位置、产出位置和验收条件。执行后登记结果、检查和待处理事项。

以一份使用指南为例，`inputs/requirements.pdf` 是收到的原始文件，`work/guide/guide.md` 是可编辑主稿。内部送审可登记历史版本，或保留 `work/guide/reviews/guide-review-01.md`。若用户要求交付 PDF，再导出 `deliverables/guide-v1.0.pdf`，并登记对应主稿版本。

## 七、可复制的项目入口模板

将以下内容复制到新项目的 `README.md`。小项目可以把第一项任务详情直接写在入口。

```markdown
# [项目名称]

## 目标
- 项目类型 [填写]
- 要解决的问题 [填写]
- 成果使用者与使用场景 [填写]

## 本阶段范围与验收
- 本阶段要做 [填写]
- 后续考虑 [填写]
- 预期成果与工作位置 [名称、路径或链接]
- 验收方式 [检查什么、怎样算通过]

## 约束与待定事项
- 已确认 [时间、资源、依赖或工作规则]
- 暂用假设 [暂按什么推进、何时核实]
- 待决定 [要决定什么、影响哪一步]

## 当前任务入口
- 看板接口 [项目概况与任务](management/project.json)
- 首项任务详情 [动作、输入、编辑位置、预期产出与检查方式]
- 任务和决策记录 [按需链接]

## 项目资料
- 正式输入与可编辑主稿 [路径或链接]
- 专题规范 [按需链接]
- 正式交付记录 [实际交付后登记]
```

## 八、初始化完成检查

- [ ] 目标、类型、本阶段范围和验收条件清楚。
- [ ] 第一项任务写清输入、动作、产出位置和完成条件。
- [ ] `work/` 和 `management/project.json` 已建立，入口能定位正式输入和工作文件。
- [ ] 接口 JSON 可解析，项目 ID 稳定，下一项任务可按 ID 定位。
- [ ] 会影响开工的假设、依赖和待定事项已经标明。
- [ ] 从入口出发，可以开始执行第一项任务。
