# 写作项目文件管理

本文是[《项目初始化文档》](Project_Initialization.md)的写作专题，适用于**编剧和小说**。立项时先确定本轮要写到哪里，例如试写一场戏、完成一集初稿、修改三章，或完成整部作品的结构稿。日常编辑使用可定位的主稿，审阅时固定基准版本，收到明确的交付指令后再按用途导出。

## 一、初始化时先确定什么

| 要确认的内容 | 编剧 | 小说 |
| --- | --- | --- |
| 作品和读者 | 短片、电影、单集或系列剧。说明阅读对象和制作或审阅场景。 | 短篇、中篇、长篇或连载。说明目标读者和阅读场景。 |
| 本阶段范围 | 如完成梗概、分场、样集、指定场次或一轮统稿。 | 如完成提纲、试写、指定章节、通稿或一轮修订。 |
| 当前写作条件 | 已有梗概、剧本或反馈，目标时长、集数、角色或制作限制。 | 已有大纲、章节或反馈，篇幅目标、叙事视角、更新安排。 |
| 第一项任务与验收 | 如完成前三场，明确开场事件、主角目标和场间衔接。 | 如完成第一章，交代当前处境，建立本章视角并留下推动后续的事件。 |

已明确的信息写入 `README.md`。会影响接下来写作的未知项记为待决定。已有稿件时，先标明**当前主稿、正在依据的提纲或设定、当前修改范围**，再开始新增或改写。

## 二、目录与文件职责

单一写作项目直接使用 `work/`。短篇小说或短剧可以从 `README.md`、`management/project.json` 和 `work/manuscript.md` 起步。有一两份辅助文件时，可直接放 `work/outline.md`、`work/characters.md` 等。文件增多后，再按实际需要建 `planning/`、`story/`、`episodes/`、`chapters/` 或 `review/`。同一项目包含写作、视频、编程等独立工作流，且确实需要分区时，可在 `work/` 下设 `writing/`，将本专题的写作文件集中到该分区。

| 位置 | 放什么 | 怎么维护 |
| --- | --- | --- |
| `README.md` | 作品目标、本轮范围、当前主稿、索引、待处理事项。 | 链接到正式记录，写清接手入口。 |
| `inputs/` | 收到的原稿、改编原作、访谈、调研原始资料和外部反馈原件。 | 保留来源和收到的版本。需要使用外部内容时，记录项目已确认的使用范围。 |
| `work/planning/` | 可编辑的创作方案、梗概、故事大纲、分场或章节计划。 | 策划文件较多时建立。策划里确定的约束可链接到已采用的设定。 |
| `work/story/` | 人物、世界设定、时间线、叙事视角和术语等供写作参照的信息。 | 设定文件较多时建立，复用信息集中维护，标明已确认项和仍在讨论的部分。 |
| `work/manuscript.md` 或稿件子目录 | 当前可编辑主稿。多集、长篇或多人分工时，按集、场或章拆分。 | 同一写作单元设一个正式编辑位置。拆分后用索引维护阅读顺序。 |
| `work/review/` | 需要单独保存的审阅快照或合并审阅稿。 | 快照固定在送审时的内容，修订回到主稿。 |
| `management/project.json` | 综合看板的项目概况与任务状态。 | 沿用主文档接口，项目类型填 `writing`。任务详情可链接到独立记录。 |
| `management/reviews/` | 审阅意见、处理决定和复核结论。 | 绑定审阅轮次、稿件基准和具体位置。小项目可把意见写进任务记录。 |
| `deliverables/`、`archive/` | 正式交付件、交付清单，或有保留价值的历史稿。 | 明确提出交付时按需使用 `deliverables/`。归档前检查旧稿是否仍被引用。 |

下文的路径以单一写作项目为例。表中的 `planning/`、`story/` 和 `review/` 都可以按需建立。

可编辑文本默认使用 UTF-8 Markdown。已有专用剧本工程、共同编辑文档或必需的修订格式时，保留其正式编辑位置，在入口登记版本和链接。收到的 PDF、Word 或其他源文件可以保留原格式。

## 三、编剧怎么管理

| 工作对象 | 位置示例 | 怎么用 |
| --- | --- | --- |
| 一句话故事、梗概、故事大纲 | `work/planning/logline.md`、`synopsis.md`、`outline.md` | 可合并成一份，或按读者和用途分开。记录已确认的主线与本轮目标。 |
| 人物与故事时间线 | `work/story/characters.md`、`timeline.md` | 维护人物目标、关系、已知信息，以及影响剧情的事件先后。 |
| 分场表 | `work/planning/scene-list.md` | 记录场次 ID、当前顺序、时间地点、出场人物、场内事件和前后依赖。 |
| 剧本主稿 | 单集用 `work/manuscript.md`，多集用 `work/episodes/ep-001.md` 等。 | 单一主稿可在场标题里写稳定 ID。有多人并行修改同一集时，可按场拆分并用索引组装。 |

分场表维护场次的**意图和计划**，剧本主稿维护实际动作和对白。写完一场后，有影响后续的变化再回填分场表。对视频制作项目，先在剧本中确定本轮采用的场次与版本，再由 AI 视频专题维护镜头及素材。剧本场次 `SCN012` 可对应多个视频镜头。

分场表可以从下面的字段开始。

| 当前顺序 | 场次 ID | 场景与时间 | 场内变化 | 前后依赖 |
| --- | --- | --- | --- | --- |
| 04 | `SCN012` | 车站大厅 · 夜 | 主角发现车票已被换掉，决定去找售票员。 | 承接 `SCN008` 的交接，触发 `SCN015` 的询问。 |

修改这场时，核对主角在入场时知道什么、离场时做了什么决定，以及下一场是否仍成立。

## 四、小说怎么管理

| 工作对象 | 位置示例 | 怎么用 |
| --- | --- | --- |
| 故事大纲与章节计划 | `work/planning/outline.md`、`chapter-plan.md` | 大纲记录整体推进，章节计划记录每章的事件、视角和预期变化。短篇可合并。 |
| 人物、设定、时间线 | `work/story/characters.md`、`world.md`、`timeline.md` | 维护跨章会用到的信息，例如年龄、地点、人物何时获知线索、哪些伏笔已回收。 |
| 正文 | 短篇用 `work/manuscript.md`，长篇可用 `work/chapters/CH012.md` 等。 | 一个章节只有一个正式编辑位置。合并通稿可用于通读、审阅和导出。 |
| 章节索引 | `work/chapters/index.md` | 按当前阅读顺序链接各章，可附卷别、标题、视角和一句话摘要。任务状态仍由看板接口或正式任务工具维护。 |

章节索引可以从下面的字段开始。

| 当前顺序 | 章节 ID | 视角人物 | 本章变化 | 稿件 |
| --- | --- | --- | --- | --- |
| 07 | `CH012` | 林岚 | 找到缺失的一页，并决定暂时瞒住同伴。 | `CH012.md` |

连载作品在用户明确要求发布时，登记实际发布的章节、版本和位置。继续修订主稿时，保留可定位的已发布版本，便于核对读者看到的内容。

## 五、编号、版本和审阅

### 5.1 编号用于定位，顺序由索引维护

- 编剧场次用 `SCN012`，小说章节用 `CH012`。编号在各自项目内保持稳定。调序时更新分场表或章节索引。
- 主稿文件可以直接用 `SCN012.md`、`CH012.md`，标题写在正文或索引。使用单文件时，在场标题或章节标题写 ID。
- 拆分或合并单元时，登记原编号对应的新位置。已经绑定某轮审阅的旧编号继续用于追溯当时的稿件。

### 5.2 主稿、审阅稿和交付稿

| 文件角色 | 示例 | 更新方式 |
| --- | --- | --- |
| 当前主稿 | `work/chapters/CH012.md` | 日常持续编辑。可用已有的文档历史或 Git 记录保存节点。 |
| 审阅基准 | `work/review/novel-review-r002.md` | 送审时固定范围和版本。有可定位历史版本时，直接登记版本链接或提交号。 |
| 审阅意见 | `management/reviews/r002.md` | 记录意见编号、场次或章节、定位短句、处理决定和复核结果。 |
| 正式交付稿 | `deliverables/novel-v001.docx` | 收到明确交付指令后按用途导出，登记对应主稿版本。 |

修改按影响范围推进。结构调整先确认场次或章节的功能与顺序，人物动机、时间线和伏笔等跨段影响随同核对。段落和语言修改在对应范围回填主稿。协作时由约定的负责人汇总意见和稿件版本，确保最终改动落到正式编辑位置。

```markdown
## r002 审阅记录

- 基准 [稿件路径、版本链接或提交号]
- 范围 [场次、章节或整稿]

| 意见 ID | 稿件位置 | 问题 | 处理决定 | 复核结果 |
| --- | --- | --- | --- | --- |
| R002-01 | CH012，「她把信折好」一段 | 角色提前知道了下一章才揭示的信息。 | 改为她看到落款后产生怀疑。 | 回看 CH012 和下一章，确认揭示顺序。 |
```

## 六、从策划到交付，每阶段更新什么

| 阶段 | 写作动作 | 记录与验收 |
| --- | --- | --- |
| 立项与策划 | 确定类型、受众、目标篇幅和本轮范围，整理已有输入。 | `README.md` 和第一项任务明确要写到哪里。 |
| 大纲与设定 | 确定故事线、人物关系、场次或章节计划。 | 保存当前采用的设定和计划，标出尚待确认的转折或约束。 |
| 初稿与统稿 | 写场次或章节，把有效内容合入主稿，按阅读顺序检查衔接。 | 稿件索引能定位正文。核对叙事视角、动机、时间线与相邻段落。 |
| 审阅与修订 | 固定审阅基准，汇总意见，按范围修改并复核。 | 重要修改能追溯到反馈或决定，未处理项回到任务记录。 |
| 内部验收 | 按本轮条件核对内容、范围、格式和稿件完整性。 | 验收结果与稿件版本对应，更新 `management/project.json` 的任务状态。 |
| 正式交付与归档 | 收到明确交付指令后，按指定对象和格式提供成果。保留继续修订需要的主稿和记录。 | 核对章节顺序、集数、版本和导出效果。根据实际交付范围决定是否需要打包。 |

看板项目类型沿用 `writing`，编剧或小说可在 `README.md` 和项目概况里标明。推进每项任务时，更新既有的任务条目与 `updated_at`。需要记录逐场或逐章的进度时，可链接分场表或章节索引。

## 七、人和 AI 的写作交接

交接时提供具体的工作范围、基准稿、相关设定和相邻内容。讨论阶段可在任务或审阅记录保留备选，采用后再写回主稿。项目长期使用 AI 协作时，可按主文档约定在 `AGENTS.md` 写明入口、主稿位置、修订边界和验收规则。

```markdown
## 任务 [简述创作或修订目标]

- 写作对象 [项目类型、场次 ID 或章节 ID]
- 当前基准 [稿件路径和适用版本]
- 参考输入 [大纲、设定、相邻场章、审阅意见]
- 修改范围 [具体段落、结构或允许改动的内容]
- 创作约束 [叙事视角、人物口吻、已确认设定、需保留的情节]
- 工作位置 [主稿或审阅记录路径]
- 验收 [要达到的效果、需核对的前后文]
- 完成记录 [改动概要、影响其他场章的事项、下一步]
```

例如，修订 `SCN012` 时可以要求「保留车票被换的事实，把主角决定去询问的动机补进本场。参考 `SCN008` 的交接和 `SCN015` 的开场。只修改 `SCN012`，完成后检查两场之间的信息是否连续」。

## 八、开工与修订检查

- [ ] 项目入口写明编剧或小说、本轮范围、主稿位置和首项任务。
- [ ] 当前采用的大纲、设定与稿件可以定位，场次或章节的阅读顺序清楚。
- [ ] 审阅意见对应具体稿件版本，修改写回正式主稿。
- [ ] 完成本轮后，已核对受影响的相邻场章、人物信息和时间线。
- [ ] 看板状态与下一项任务已更新。正式交付时，登记提供的稿件版本与位置。
